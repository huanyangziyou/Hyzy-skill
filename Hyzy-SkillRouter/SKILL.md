# Skill 治理层路由

这是一组「管 Skill 本身」的 Skill 的统一入口。它们不产出领域内容，只负责：找现成、造新的、改到能公开、验收、盘点维护。

**为什么需要这一层**：这 5 个成员的触发词大量重叠（都含「skill」二字），单靠各自的 description 容易选错。先用本文件定位，再加载对应成员，比让模型自己猜稳。

## 一、路由表

先查这张表，再加载成员。**不要凭 description 猜。**

| 你的处境 | 走向 | 一句话判据 |
|---|---|---|
| 不确定有没有现成 Skill 能做这件事 | `find-skills` | 还没开始造，先看别人做过没有 |
| 要新建 Skill / 把流程封装成 Skill | `Hyzy-startupSkill` | 有可复用的固定流程，缺的是包 |
| 已有 Skill 要换机器、要去私有信息、要公开 | `Hyzy-skillPortable` | skill 已经能跑，问题是可移植性 |
| 要宣称「完成 / 已修复 / 已通过 / 已上传 / 已安装 / 已公开」 | `Hyzy-VerifyGate` | 横切闸门，每次交付都要过 |
| 库变乱了：查重复、找空壳、要盘点 | `skill-library-governance` | 面向整个库，不是单个 skill |

**「加载」的意思**：读 `<库根>/<成员目录>/SKILL.md`，然后按它执行。不是把它的方法论搬到这里来。

### 歧义消解（两两最易混的）

| 分不清 | 判据 |
|---|---|
| `find-skills` vs `Hyzy-startupSkill` | 先有「查」再有「造」。`startupSkill` 会先调 `find-skills`；已确定要造就直接进 `startupSkill` |
| `Hyzy-startupSkill` vs `Hyzy-skillPortable` | 造新的 vs 改旧的。连包都没有 → `startupSkill`；有包只是不通用 → `skillPortable` |
| `Hyzy-skillPortable` vs `skill-library-governance` | 改一个 vs 看一库。前者写文件，后者只读出报告 |
| `Hyzy-VerifyGate` vs 其他四个 | 它不是流程的一环，是横切闸门。任何成员交付前都要过 |

## 二、三条主线

下面只写**步骤名与串联顺序**。每个步骤「怎么做、判据是什么」在成员自己的文件里，本节不复述——复述会两处不同步。

**造一个新 Skill**
1. `find-skills` 查现成（只读；命中可复用就停，不要重复造）
2. `Hyzy-startupSkill` 建包
3. `Hyzy-VerifyGate` 验收

> 第 1 步与 `Hyzy-startupSkill` 自己的第一步是同一件事。**直接进 `startupSkill` 时不要在前面再跑一遍 `find-skills`**——它内部会调。只有「先看看有没有现成的、再决定造不造」这种还没定方向的处境，才从第 1 步起。

**把一个已有 Skill 变成能公开的**
1. `Hyzy-skillPortable` 探查改造（先备份，再逐处替换）
2. `Hyzy-VerifyGate` 验收（产出证据三件套，定义见 members.md）
3. 公开前问一句：目标仓库是公开还是私有——**这一步归你，不归任何成员**（成员只管改包，不管发布）

**维护整个库**
1. `skill-library-governance` 全量体检（只读，出报告与建议）
2. 逐项拍板后才处置（先入暂存区，不物理删除）
3. `Hyzy-VerifyGate` 核对处置结果

三条主线的共同点：**每一步都有「不许省的那一步」**——查现成不能跳、备份不能跳、验证不能跳。跳掉哪一步，后面都要重做一遍。

## 三、硬规则

1. **先路由，再动手**：不确定走哪个成员时读第一节，不要凭 description 猜。猜错的代价是走错流程、白做一遍。
2. **只读成员不得写文件**：`find-skills` 与 `skill-library-governance` 全程只读。它们给出建议后，处置动作必须另起一轮并取得明确同意。
3. **不许绕过 VerifyGate**：任何「完成 / 已修复 / 已通过 / 已上传 / 已安装 / 已公开」的结论，必须附本轮实跑的证据三件套。没跑过就写「没跑过」。
4. **成员缺失要明说**：路由表里某个 Skill 在当前库不存在时，直接告诉用户「未安装 X」，不要用相近成员顶替。
5. **不代做成员的事**：本 Skill 只负责定位与串联。第二节里出现的只是**步骤名**（「查现成」「建包」「先备份」「全量体检」这类），不是这些步骤的判据、公式或规则清单——那些在成员自己的文件里。判据只在成员那里写一次。

## 四、不能做的事

- 不执行领域任务：写报告、转 Markdown、画链路图、做实验报告、写成长笔记 → 见第六节，那里点名去哪。
- 不在没读路由表的情况下下结论「该用 X」。
- 不把 `find-skills` 的候选清单当成「已安装」；它默认只列不装。
- 不把 `skill-library-governance` 的报告当成处置授权；它只提建议。
- 不在成员缺失时编造一个不存在的能力。
- 不重复成员 Skill 的正文内容。

## 五、输出格式

路由判断固定三行，不超过三行：

```text
判断：<去哪>
依据：<路由表哪一行 / 哪条歧义判据 / 第六节哪一行>
下一步：<加载哪个成员、它的第一步是什么>
```

若两个成员都像，仍用这三行，只是内容换写法：

```text
判断：<A> 或 <B>（两可，未定）
依据：<两句各自边界，说明卡在哪>
下一步：先问 —— <一个能分开它们的问题>
```

问完、拿到回答，再落成第一个格式里的单一成员。**不要把两个候选都写进「下一步」**——那等于把选择推回给用户却不给判据。

本 Skill 不产出文件；它的产物就是这段判断。

## 六、本层管不到时去哪

治理层只管「skill 本身」。用户要的是一个**领域产物**时，本层不接管，但要说清去哪——只说「走对应领域 Skill」等于没说。

| 用户想要 | 直接去 |
|---|---|
| 录音稿 / 网页 / docx → 干净 Markdown | `Hyzy-rawprocess` |
| 成套 PDF 教材 → 概念笔记库 | `Hyzy-PDFtomdnotemap` |
| 叙述型知识 → 可执行方法路径 | `Hyzy-KnowtoMethPath` |
| 源码 → SVG 链路图 + 逐级解释 | `Hyzy-HDLtoSVG&Explain` |
| 一期细分行业深度研究报告 | `Hyzy-IndustryRadar` |
| 原始数据照片 → 规范物理实验报告 | `Hyzy-PhysLabReport` |
| AI 协作经历 → 成长笔记 | `Hyzy-AIGrowthNote` |

上表只给**去向**，不给做法；这七个的触发条件与方法论在各自 `SKILL.md`。表里某一行对应的目录不存在时，按「成员缺失」处理：直说未安装，不拿相近的顶替。

**这一节的输出比第一节短**：members.md 只覆盖治理层五个，所以走第六节时，「下一步」只写到「加载 `<该成员>`，读它自己的 SKILL.md」为止——**不要替它编一个第一步**，你没读过它的文件。
