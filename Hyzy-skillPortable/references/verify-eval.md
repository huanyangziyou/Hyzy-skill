# 验证与评测：保真四道、行为测试、性能怎么测

第 5 步验证前必读。核心区分：**「改对了」和「改好了」是两件事**——前者靠保真校验，后者靠评测。先保证没改坏，再谈有没有变好。

## 一、证据分级（报结论时必须标注级别）

| 级别 | 含义 | 本 skill 里的典型动作 |
|---|---|---|
| 1 结构校验 | 文件能解析、引用都存在、表格不塌 | 表格列数、代码围栏配对、references 路径存在性 |
| 2 保真校验 | 该留的一个没丢 | 数字比对 + 关键词清单 |
| 3 行为测试 | 代理按新结构真的会做对 | 让一个不知道背景的代理跑同一道题 |
| 4 对照评测 | 改前 vs 改后有可比的差异 | A/B 双盲 + 耗时拆解 |

**只报实际达到的最高级，并写明下一级缺什么证据。**「我改完检查过了」不算任何一级。

## 二、保真四道

### 第 1 道：数字比对（对抗「顺手删掉一个阈值」）

把旧版所有数字抽出来做多重集比较，新版数量不足的逐个解释：

```python
import re
from collections import Counter
nums = lambda t: Counter(re.findall(r'\d[\d,.]*', t))
lost = [(k, v, nums(new)[k]) for k, v in nums(old).items() if nums(new)[k] < v]
```

**每个「丢失」都要给理由**。合法的理由只有几类：路径被占位符替换、日期被抽象、示例改名。如果某个数字的丢失理由说不出来，就是真丢了。

反向也要看：新增数字应该都是你有意补的（补的解释、补的校准值）。

### 第 2 道：关键词清单（对抗「整段消失」）

手写一份 30–80 项的清单，覆盖：所有阈值与尺寸、章节名、命令模板、硬边界条目、专有判据。

```python
checks = [("1433 页","1433"), ("多书对照 ≥2 本","多书对照 ≥2 本"), ...]
miss = [n for n, k in checks if k not in new]
assert not miss, miss
```

条目要**具体到能被 grep 到**。「流程完整」这种没法验，不算条目。

### 第 3 道：结构校验

- 表格：同一表格块内每行列数必须等于表头列数（改表格最容易漏一列）
- 代码围栏：``` 数量为偶数
- 引用：文档里出现的 `references/xxx.md`、`scripts/xxx.py` 必须真实存在
- frontmatter：`name/description/category` 三个字段在行首、`description` 单行

### 第 4 道：行为测试（最容易被跳过，但最有用）

派一个**不知道改造背景**的代理，只给它 skill 路径和一道真实题目，看它：

- 是否按「必读」标记读了该读的 references
- 是否把该推迟的 references 正确推迟
- 引用的数字/坐标/色值能否说出出处
- 会不会去读被隔离的本机默认值段

能读出结构与出处，才说明拆分和抽象化没有破坏可执行性。**光看文件长得对不算验过。**

## 三、效果评测：改前 vs 改后

想让结论站得住，做双盲对照：

1. 同一批题目（4 道以上，覆盖主要触发场景），新旧两版各跑一遍。
2. **不给裁判看版本号**，顺序打乱。
3. 评分维度先定死（如：答对率 / 是否多问无用问题 / 是否引错来源 / 是否越界动文件）。
4. 记录原始打分，不只记结论。

读结果时注意：

- 单样本不足以下结论，至少说明「n=4，方向一致但样本小」。
- **差异集中在哪一类题上，比总分更有信息量**（例如「4/4 赢在不再多问一轮」）。
- 赢了也要写清「赢得的是什么」——是少问了一轮，还是答得更准，两者不能混。

## 四、性能测试：先拆，再测

### 别把代理指标当墙钟

「调用次数减少」「脚本重写次数下降」都只是**机械步骤的代理指标**，不等于耗时下降。把它们说成「更快」是典型的过度声称。

### 耗时拆解（测之前先估，估完再决定测不测）

| 段 | 内容 | 改造能不能动它 |
|---|---|---|
| T1 摄取 | 读源材料、读规范 | 基本动不了，由任务体量决定 |
| T2 生成 | 模型写产物 | 能减少轮次（少问、少返工），但难量化 |
| T3 机械 | 本地化、校验、格式处理 | **改造主要影响这里** |
| T4 重跑 | 失败重试、路径断裂重跑 | **改造能真正消除的部分** |

结论：T3/T4 通常占比小，**所以单次任务墙钟不会因 skill 优化而明显变快**。真实收益在「消除 T4 重跑」和「降低 T2 轮次」。

### 想真测耗时，这样做

- 用固定输入跑 3 次以上，记录墙钟，报中位数与范围，不报单次。
- 同时记录「是否需要人工介入 / 是否重跑」，这比秒数更能说明稳定性。
- **不做精确计时就别给秒数**。宁可写「消除了 2 处必然重跑」，也不要编一个「快了 30%」。

### 分阶段对比（长期迭代时用）

以改动时间戳为分界，划出「原始态 / 首次固化 / 首次验证 / 二次优化」等阶段，每阶段比三个维度：效率（调用数、重写数、重跑数）、时间（一次性投入 vs 每任务墙钟）、资源（留存资产、图序确定性、一致性）。

## 五、诚实结论模板

四类标签，一个结论里可以同时出现：

| 标签 | 什么时候用 |
|---|---|
| **设计优势** | 结构上更合理，但没测过 |
| **已验证优势** | 有对照数据支持（写明 n 与维度） |
| **假设** | 合理但未验证，写明怎么验 |
| **missing evidence** | 本该有但没有，写清缺什么 |

示例（真实可用的写法）：

> 拆分后代理能按标记读到正确 references（**已验证**，n=1 行为测试）；预计减少无关上下文载入（**假设**，未测 token）；墙钟是否下降**missing evidence**——本轮无计时，且 T3 占比小，预期变化不显著。

反面写法（禁止）：「优化后更高效、更专业、结构更清晰」。这些词无法检验，等于没说话。

## 六、假信号清单

| 看着像成功 | 实际是什么 |
|---|---|
| 两库 byte 比对大量不一致 | 多半是 CRLF/LF 差异，先归一化 |
| 脚本 `rc=0` | 不代表动作生效，`rm` 静默失败很常见，删完必须复扫 |
| 校验器只输出「通过」 | 没做负样本测试，校验器本身不可信 |
| 文档说「已处理」 | 假账高发区，回到文件里 grep 确认 |
| 分类计数为 0 | 先确认正则没写错（中文字符类、转义层级） |

## 七、收尾必须回答的三个问题

1. 最高验证等级是几级？下一级缺什么？
2. 有没有「判不了」的项？为什么判不了？
3. 留下的副产物清干净了吗（`__pycache__`、临时包、测试脚本）？
