# 个人 Skill 创建与优化器

把反复做的方法论变成最小可安装文件包，或对已有 skill 做只读审计与改造规划。选中后由本 skill 独占创建流程，不再调用其他 skill creator，避免双重初始化与重复提问。

> **选型与信息恢复之前必读 `references/env-adapt.md`**（skill 库根 / 记忆目录 / 需求 SSOT 的存在才读规则、写入权限边界）。

## 一、路由与权限

| 动作 | 写入权限 | 交付物 |
|---|---|---|
| 审计 / 规划 / 评测 | **只读，零写入** | 报告与建议 |
| 创建 / 改造 | 仅授权目录 `skills/<name>/` 内写入 | 文件包 |
| 安装 / 刷新索引 / 提交 | 需明确授权 | 索引与版本记录 |

- 带「先看看」「先规划」「不要改」的请求一律按只读处理。
- **覆盖、删除、移动、重命名用户文件前必须二次确认**；删除先入库外暂存 `_skill_backup_<date>/`，禁止裸删。
- 权限不足时停在写入之前，说明缺哪项授权。

## 二、选型与信息恢复

**先查现成（创建 / 改造类请求前置）**：动手写之前先只读检索是否已有可复用方案——读 `INDEX.md` 与各 `SKILL.md`，必要时调 `find-skills` 查 skills.sh / GitHub / SkillHub。命中可复用 → 先给「复用或改造」建议，不新建，除非用户明确要新建；未命中 → 继续本节流程。此步只读、不安装、不写文件，且不得因此增加澄清轮次（仍是最多问一个边界问题）。

**选型 3 问**（依据 `ARCHITECTURE.md` 第 1 节）：一次性 → 建议一段 prompt；反复 + 流程固定 → 继续；反复 + 大量专属资料 → Skill + RAG 壳；全新能力 → fine-tune，超出范围。不硬造 Skill。

**复盘记忆**：读 `.workbuddy/memory/` 每日日志、`MEMORY.md`、已安装 skill，提炼反复模式与既有方法论，并引用来源路径告知用户；若当前项目目录存在需求 SSOT（默认 `需求说明.md`），先读它，不存在则不创建、不追问。这是「入库 → 提问 → 沉淀」闭环的入口，不可省略。

**从对话与材料恢复五要素，不做问卷**：

| 要素 | 说明 |
|---|---|
| 重复问题 | 用户到底反复在解决什么 |
| 真实输入 | 实际会给出的材料 / 命令 / 文件 |
| 成品 | 交付物形态与路径 |
| 完成证据 | 怎样算做成了 |
| 最近排除项 | 最像但不该由本 skill 接的任务 |

信息足够 → 直接做，不提问。仅当一个缺失答案会改变**产品类别、权限边界或不可逆范围**时，问**一个**问题并说明它改变什么；其余缺项写保守可逆假设后继续。禁止把澄清拆成多轮问卷。

## 三、最轻包设计

模式由 Agent 按复用范围、风险、平台、发布需求推断，不让用户选。

- 默认 **Scaffold**（个人本地可逆）：根 `SKILL.md` + 任务真正赚到的资源，结构校验通过即可交付。
- 团队复用、触发易误伤、跨平台、高风险权限、公开发布或用户明确要求评测 → 升级门禁，补触发案例与验证证据。
- **不为个人本地 skill 造** README、manifest、Skill IR、发布脚本、报告目录或空目录。

| 资源 | 放什么 |
|---|---|
| `SKILL.md` | 触发边界、关键判断、主流程、输出合同 |
| `references/` | 判断方法、长示例、政策，按决策按需加载 |
| `scripts/` | 确定性、易错、可测试的动作，装前必审计 |
| `evals/` | 应触发 / 不应触发 / 近邻样例 |

一个包只能有一个可发现的根 `SKILL.md`；内嵌示例用 `SKILL.example.md` 或 `SKILL.fixture.md`。核心 ≤ 5000 字，超了按决策边界拆 `references/`。

## 四、写行为规则与泛化门

按 `references/skill-template.md` 写。要点：

- 指令写成 `当 <可观察条件>，做 <具体动作>，验证 <检查>，然后 <继续或停止>`。
- 约束分三级：**硬约束**（违反即失败）/ **推荐默认**（有反例才偏离并记理由）/ **允许自主判断**（在命名边界内自选）。
- 必带停止条件、失败处理表、可验收标准；删掉「专业、高效、全面」等不可检验词。
- 角色描述只在改变决策、术语、安全或输出时才写。

**泛化门**：单样本反馈先改写成领域中立失效机制 → 分类为「核心不变量 / 可选适配 / 仅 eval fixture」→ 只有安全、事实、权限或跨领域复现 ≥ 2 次才升核心规则。一次性细节留在 fixture 或专门 reference，防止把一次纠正过度推广。详见 `references/authoring-method.md`。

## 五、验证与证据边界

| 级别 | 含义 |
|---|---|
| 1 结构校验 | frontmatter、引用路径、资源与脚本静态检查通过 |
| 2 真实任务冒烟 | 至少完成 1 个真实主要任务并通过验收 |
| 3 留出与回归 | 留出样例通过且无关键回归 |
| 4 安装核对 | 安装来源可装，内容与源目录逐项一致 |

只报实际达到的最高级，说明下一级缺什么证据。改过 `description` 必须复核 `evals/trigger_cases.json` 的正例、负例与近邻样例。

优化类结论必须区分**设计优势 / 已验证优势 / 假设 / missing evidence**。不能把「调用步骤变少」当成「墙钟变短」：耗时拆解 T1 摄取 / T2 生成 / T3 机械 / T4 重跑，skill 改造通常只动 T3 与 T4，见 `references/eval-method.md`。不得在无实跑对比时声称生成结果更优。

## 六、交付与治理

1. 先给「选型结论 + 现成检索结果 + 记忆复盘摘要（含来源路径）」。
2. 再给完整 `SKILL.md`（代码块）或只读审计报告。
3. 最后给安装与迭代：写入 `skills/<name>/` → `python tools/refresh_index.py` → 提交 git → 3–5 轮真实任务迭代。**工作区已有无关改动时不代为提交**，先报告状态。
4. 收尾写明：路径、解决的问题、最高验证等级、未验证风险。

## 七、不能做的事（违反即失败）

- 审计 / 规划类请求不得写任何文件。
- 未二次确认不得覆盖、删除、移动或重命名用户文件。
- 不得 `rm -rf` / `del /S /Q` 裸删，删除先入库外暂存。
- 不得编造用户未确认的身份、数据、边界或完成证据。
- 不得为一次性需求强造 Skill，不得生成含第二个根 `SKILL.md` 的包。
- 不得产出未审计脚本而不提示风险（网络外发 / 破坏命令 / 密钥 / 注入）。
- 不得在 Scaffold 级强塞 eval、报告或发布物。
- 不得把设计优势包装成已验证优势。
