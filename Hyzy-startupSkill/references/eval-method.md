# 优化有效性评估方法

> 用于回答「这次 skill 改造有没有变好 / 有没有变快」。目标是把可验证的和推测的分开。

## 一、耗时拆解（优化前必做）

| 段 | 内容 | 常见占比 | skill 改造能否影响 |
|---|---|---|---|
| T1 摄取 | 读源材料、盘点文件 | 中 | 几乎不能 |
| T2 生成 | LLM 写产物 | **最大** | 只能通过降低生成轮次间接影响 |
| T3 机械 | 本地化、格式化、校验 | 小 | **主要可动区** |
| T4 重跑 | 失败后整轮重试 | 波动大 | **收益最明显（消除重跑）** |

单次任务主要耗时是 T1 + T2，改造通常只动 T3，因此**单次墙钟不会因 skill 优化明显变短**。

## 二、代理指标陷阱
Bash 调用次数下降、脚本重写减少，只是机械步骤的代理指标，**不等于墙钟耗时下降**。无精确计时不得把调用数当秒数用。

## 三、分阶段对比法
以 skill 落地时间戳分界：原始态 / 首次固化 / 首批验证 / 复盘 / 二次优化 / 二次验证。每阶段对比三维：

1. 效率：调用数、重写、重跑次数
2. 时间：一次性沉没投入 vs 每任务墙钟（分开记）
3. 资源：留存资产、图序确定性、跨次一致性

## 四、优先改落地层，而非调用层
首跑失败的根因常在命令模板（如 Git Bash 下 `$HOME` 为空导致路径断裂），不在脚本本身。模板用绝对路径可根除整轮 T4 重跑。这类修复比再优化一轮提示词更值。

## 五、诚实局限清单
- 单样本不足以证明普遍收益
- 任务体量不同（轻 / 重任务）墙钟不可直接比
- 无精确计时，只有调用数代理
- 预测性「消除重跑」需多样本确认

结论必须区分「稳定性 / 复用性提升」与「墙钟缩短」，不可混为一谈。

## 六、证据标注
| 标签 | 含义 |
|---|---|
| 设计优势 | 结构上应当更好，无实跑证据 |
| 已验证优势 | 有真实任务对比且通过验收 |
| 假设 | 待验证的推断 |
| missing evidence | 缺计时 / 留出样本 / 对比数据，不能下结论 |

`recorded_fixture` 只说明样例可复现，不算模型实跑证据。本地校验通过不等于生成结果优于其他方案。
